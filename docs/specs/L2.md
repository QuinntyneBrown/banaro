# L2 - Detailed Requirements

Conventions used throughout:

- Viewports: XS < 576 px, SM ≥ 576 px, MD ≥ 768 px, LG ≥ 992 px, XL ≥ 1200 px.
- "Member" is a signed-in, e-mail-verified user. "Visitor" is anyone not signed in.
- All API paths are under `/api/v1`. Every endpoint requires authentication unless a requirement says it is anonymous.
- Each acceptance test file must carry a header comment naming the L2 requirements it covers:
  `// Acceptance Test` / `// Traces to: L2-0xx` / `// Description: ...`.
- Screen and state names refer to `docs/mocks/pages|dialogs|notifications/<name>/<state>.html`.

---

## L2-001: Join Banaro
**Traces to:** L1-001

A visitor must be able to create an account with name, e-mail and password and must agree to the code of conduct. Passwords must be at least 12 characters and must not be on a common-password list. The e-mail address must be unique case-insensitively.

**Acceptance Criteria:**
1. Given a visitor on `/join`, when they submit a valid name, unused e-mail, a compliant password and tick the code-of-conduct box, then an account is created in an unverified state, a verification e-mail is queued, and the success state is shown.
2. Given a visitor submits an empty name, a malformed e-mail, a password under 12 characters, or without agreeing to the code of conduct, when the form is submitted, then no account is created, the API returns 422 with per-field errors, and the invalid state shows each error next to its field and moves focus to the first invalid field.
3. Given an account already exists for `Amara@Example.com`, when a visitor joins with `amara@example.com`, then no second account is created and the response does not reveal that the e-mail is registered (same success state, and a "you already have an account" e-mail is sent to the address).
4. Given the form is being submitted, when the visitor looks at the page, then the submit button is disabled and shows a busy label, and a second submission cannot be triggered (submitting state).
5. Given a password is submitted, when it is stored, then it is hashed with a salted adaptive algorithm (bcrypt cost ≥ 12 or argon2id) and never logged or returned.
6. Given more than 5 join attempts from one IP within 10 minutes, when another is made, then the API returns 429 with a `Retry-After` header.

## L2-002: Verify e-mail address
**Traces to:** L1-001

A new account must verify its e-mail address through a signed, single-use, expiring link before using member features.

**Acceptance Criteria:**
1. Given a verification e-mail sent less than 24 hours ago, when the visitor opens its link, then the account becomes verified and the success state of `verify-email` is shown with a path to onboarding.
2. Given a link older than 24 hours, a link with a tampered signature, or a link already used, when it is opened, then the account stays unchanged and the error state offers to send a new link.
3. Given an unverified member, when they request a new link, then a new e-mail is queued, earlier links stop working, and no more than 3 requests per hour are accepted per account (429 afterwards).
4. Given an unverified member signs in, when they request any member-only endpoint, then the API returns 403 with code `email_unverified` and the app routes them to `verify-email`.

## L2-003: Sign in and sign out
**Traces to:** L1-001, L1-014

A verified member must be able to sign in with e-mail and password, and sign out, with protection against credential guessing.

**Acceptance Criteria:**
1. Given valid credentials for a verified account, when the member submits `/sign-in`, then a session is created, a new session identifier is issued, and they land on the dashboard (or the page they were sent from, if it is a same-origin path).
2. Given a wrong e-mail or wrong password, when the form is submitted, then the error state shows one generic message ("Those details don't match") that does not say which was wrong, and the response time does not differ measurably between unknown and known e-mails.
3. Given 5 failed attempts for one account or 20 from one IP within 15 minutes, when another attempt is made, then the API returns 429 and the form shows a "try again in N minutes" message.
4. Given an invalid form (empty or malformed fields), when submitted, then the invalid state shows field errors without calling the API.
5. Given a member who chose to sign out, when they choose "Sign out" in the account menu, then the server session is destroyed, the cookie is cleared, and the signed-out state of `sign-in` is shown.
6. Given a `returnTo` parameter that points to another origin, when sign-in succeeds, then it is ignored and the member lands on the dashboard.
7. Given the session cookie, when it is issued, then it is `HttpOnly`, `Secure`, `SameSite=Lax`.

## L2-004: Recover a forgotten password
**Traces to:** L1-001

A person must be able to reset a forgotten password by e-mail without learning whether an address is registered.

**Acceptance Criteria:**
1. Given any well-formed e-mail on `/forgot-password`, when submitted, then the success state is shown and an e-mail with a reset link is sent only if an account exists.
2. Given a reset link less than 60 minutes old, when the person opens it and submits a compliant new password, then the password changes, every existing session for that account is revoked, and the success state links to sign-in.
3. Given an expired, used or tampered reset link, when opened, then the error state of `reset-password` offers to request a new link.
4. Given a new password under 12 characters or equal to the old one, when submitted, then the invalid state shows the specific problem.
5. Given more than 5 reset requests per e-mail or IP within an hour, when another is made, then the API returns 429.

## L2-005: Session expiry and recovery
**Traces to:** L1-001, L1-013

When a member's session expires while they work, the app must let them sign in again without losing work.

**Acceptance Criteria:**
1. Given a session that has expired, when any API call returns 401, then the `session-expired` dialog opens over the current page, focus moves into it, and the page state (including unsent form input) is preserved.
2. Given the dialog is open, when the member submits a correct password, then the dialog shows busy, closes on success, and the original action is retried once.
3. Given a wrong password in the dialog, when submitted, then the invalid state shows an error and the dialog remains open; given a network or server failure, then the failed state shows a retry action.
4. Given the member chooses "Sign out" in the dialog, when selected, then they are taken to `/sign-in` and the preserved input is discarded.
5. Given an idle session, when 30 days pass without activity, then the server expires it; an active session has an absolute lifetime of 90 days.

## L2-006: Onboarding
**Traces to:** L1-002

After verifying their e-mail, a new member must be guided through a short onboarding that captures role, neighbourhood, skills and goals.

**Acceptance Criteria:**
1. Given a verified member with an incomplete profile, when they sign in, then they are routed to `/welcome` before any other member area, and the app can resume at the first unfinished step.
2. Given the skills step, when the member selects skills from the catalogue or adds custom ones, then up to 12 skills are saved in order, and a 13th is rejected with an explanatory message.
3. Given the goals step, when the member chooses one or more of "Co-founding", "Advising" and "Contributing", then those are saved as their "Open to" values.
4. Given a required field (role, neighbourhood) is missing, when the member continues, then the invalid state shows field errors and nothing is saved for the step.
5. Given all steps are saved, when the member finishes, then the profile is marked complete, the success state shows, and the member lands on the dashboard.
6. Given the member leaves partway, when they return, then previously saved steps are retained.

## L2-007: View and edit own profile
**Traces to:** L1-002

A member must be able to view how their profile appears to others and edit it.

**Acceptance Criteria:**
1. Given a member, when they open their own profile, then the `own` state shows an "Edit profile" action and no "Say hello", "Report" or "Block" actions.
2. Given `/profile/edit`, when the member changes name, headline role, neighbourhood (from the GTA neighbourhood list), bio (≤ 500 characters), skills (≤ 12), experience entries, links, "Open to" and the product they are building, and saves, then the profile reflects the change after reload.
3. Given invalid values (bio > 500 characters, malformed link URL, unsupported neighbourhood), when saved, then the API returns 422 and the invalid state shows field errors.
4. Given the save is in flight, when the member looks at the form, then the save button is disabled and busy, and the submitting state is shown; on success the success state shows a confirmation toast.
5. Given the edit form cannot load or save due to a server fault, when it fails, then the error state shows a retry action and entered values are retained.
6. Given any text in a profile, when rendered anywhere, then it is output-encoded so that markup in a name, bio or link label is shown as text.
7. Given a profile is loading, when data has not arrived, then the loading state shows skeletons sized to the final layout.

## L2-008: Profile photo
**Traces to:** L1-002

A member must be able to set, change and remove a profile photo through the `change-photo` dialog.

**Acceptance Criteria:**
1. Given a JPEG, PNG or WebP image of at most 5 MB and at least 480 × 480 px, when the member uploads it and confirms a square crop, then a 480 × 480 px image is stored and shown in place of their initials.
2. Given a file of another type, over 5 MB, under 480 px on a side, or whose content does not match its declared type, when uploaded, then it is rejected and the invalid state names the problem.
3. Given an upload in progress, when the dialog is open, then it shows busy and cannot be dismissed accidentally; on server failure the failed state offers retry.
4. Given an uploaded image, when stored, then metadata (including GPS EXIF) is stripped and the file is scanned before it becomes visible.
5. Given a member with a photo, when they choose "Remove photo", then the initials tile is shown again and the stored file is deleted.

## L2-009: Browse and search the builder directory
**Traces to:** L1-003

Members and visitors must be able to browse builders at `/builders`, 12 per page, sorted by best match by default.

**Acceptance Criteria:**
1. Given the directory, when it opens, then it shows the result count ("1,284 builders in Toronto and the GTA" style), the first 12 builders as cards with photo or initials, name, role, neighbourhood, distance, skills, "Building" and "Open to" facts, and an online status shown as a word as well as a dot.
2. Given a signed-in member with a neighbourhood, when the default sort "Best match" applies, then results are ordered by match score descending, with ties broken by most recently active.
3. Given the sort control, when the member chooses Nearest, Recently active or Newest, then results re-order accordingly and the choice is reflected in the URL.
4. Given the search box, when the member types a name, skill or project name, then results are filtered after a 250 ms pause, case- and accent-insensitively.
5. Given more than 12 results, when the member pages, then page N shows items (N−1)×12+1 to N×12 and the URL holds the page number; a page beyond the last returns the last page.
6. Given a visitor who is signed out, when they open the directory, then they see cards limited to name, role, neighbourhood, skills and photo, without match score, exact distance, online status or messaging actions.
7. Given the directory is loading, when results have not arrived, then the loading state shows 12 skeleton cards; given a server failure, then the error state shows a retry action.

## L2-010: Filter the builder directory
**Traces to:** L1-003

Members must be able to narrow the directory with facet filters that combine predictably.

**Acceptance Criteria:**
1. Given filters for Role, Open to, Neighbourhood/city, Distance and Skills, when the member selects values, then results match all filter groups (AND) and any value within a group (OR), and each option shows its count.
2. Given Distance, when no value is chosen, then results are limited to builders within 40 km of the member's neighbourhood; the options are 5, 10, 25, 40 km and "Anywhere in the GTA".
3. Given filters are applied, when the page reloads or the URL is shared, then the same filters and results are restored from the query string, and a "Clear all" action resets them.
4. Given filters match no builder, when results return, then the no-results state shows the active filters, a "Clear all" action and a suggestion to widen distance.
5. Given skill filters, when rendered, then each skill is a toggle button with `aria-pressed`, and filter groups are `fieldset`/`legend`.
6. Given viewport < 992 px, when the member taps "Filters", then filters open as a bottom sheet with an "Apply" action and focus management; at ≥ 992 px they are a sticky sidebar.
7. Given an unusually long name, a builder with no skills or a builder with no photo, when rendered (edge state), then the card truncates with an ellipsis, omits the empty row, and shows initials respectively without shifting layout.

**Traces to:** L1-003

A member must be able to open another builder's profile and see what they offer, subject to that builder's privacy settings.

**Acceptance Criteria:**

5. Given a profile is loading or failed, when opened, then the loading and error states are shown, the latter with retry.
6. Given a member views a profile, when they use "Say hello", "Report" or "Block", then the corresponding dialogs open (L2-026, L2-031, L2-032).

A member must be able to share a product in progress at `/projects/new`.

Given a member, when they submit a name (≤ 80 characters), one-line description (≤ 140), longer description (≤ 2,000), stage (Idea, Design, Prototype, Beta, Pilot, Launched), "looking for" roles (zero or more of Co-founder, Technical co-founder, Contributor, Advisor, Designer, Engineer), and optional link, then the project is created owned by them, and the success state links to its page.

## L2-014: Edit and delete a project
**Traces to:** L1-004, L1-014

Only the owner may change or remove a project.

**Acceptance Criteria:**
1. Given the owner on `/projects/{id}/edit`, when they save valid changes, then the project updates and the owner returns to its page with a success toast; invalid values show the invalid state; in-flight shows the submitting state.

4. Given the owner confirms, when deletion runs, then the project, its feedback and help offers are removed, the dialog shows busy then closes, and the member lands on their dashboard with a toast.
5. Given deletion fails, when the server errors, then the failed state shows a retry action and the project remains.

## L2-020: RSVP, waitlist and cancel
**Traces to:** L1-006

A member must be able to RSVP to an event with capacity, join a waitlist when it is full, and cancel.

**Acceptance Criteria:**
1. Given an event with spots left, when a member selects "RSVP", then they are added as going, the spots-left count falls by one atomically, and the `rsvp-toast` success message appears.
2. Given an event at capacity, when a member selects "Join waitlist", then they are added at the end of the waitlist and shown their position.
3. Given 63 of 64 spots taken and two members RSVP simultaneously, when both requests arrive, then exactly one is going and the other is waitlisted; capacity is never exceeded.
4. Given a member who is going, when they confirm the `cancel-rsvp` dialog, then their RSVP is removed, and the first waitlisted member is promoted and notified.
5. Given the RSVP or cancel request fails, when the server errors, then an `rsvp-toast` danger message and the dialog's failed state offer retry, and no count changes.
6. Given a member already going, when they RSVP again, then the API is idempotent and returns the existing RSVP.
7. Given an event that has started or ended, when a member attempts to RSVP, then the API returns 422 `event_closed`.

## L2-022: Weekly match suggestions
**Traces to:** L1-007

The system must suggest three nearby, compatible builders to each active matching member every Monday.

**Acceptance Criteria:**
1. Given a member with active preferences, when the Monday job runs (06:00 America/Toronto), then it creates exactly three suggestions drawn from builders who are open to the matching role, within the member's distance, not blocked in either direction, not already suggested or passed within the last 90 days, and ordered by match score.
2. Given fewer than three eligible builders, when the job runs, then it creates only those that exist and does not pad with ineligible builders.
3. Given the job runs twice for the same week (retry), when the second run starts, then no duplicate suggestions are created.
4. Given the match score, when computed, then it is an integer 0–100 derived from skill complement, "open to" alignment, distance and recent activity, and the weights are documented and covered by service tests.
5. Given suggestions were created, when the member next opens the app, then the dashboard badge shows the count of unreviewed matches and a notification is sent (L2-029).

## L2-026: Say hello and hold conversations
**Traces to:** L1-008

A member must be able to send a first message to another builder and continue the conversation in `/messages`.

**Acceptance Criteria:**

9. Given a member opens a conversation, when they read a thread, then only participants can fetch it; any other member receives 404.

## L2-028: System notifications (toasts and banners)
**Traces to:** L1-009, L1-013

The app must communicate transient and persistent messages consistently using toasts, RSVP toasts, account banners, site banners and connection banners.

**Acceptance Criteria:**
1. Given an action completes, when feedback is needed, then a toast of variant info, success, warning or danger appears, announced to assistive technology (`role="status"`; danger uses `role="alert"`), and success and info toasts dismiss after 6 seconds while warning and danger toasts remain until dismissed.
2. Given multiple toasts, when they stack, then at most 3 are visible, the newest on top, and the rest queue.
3. Given a toast with an action (for example "Undo"), when the action is selected, then the action runs once and the toast closes.
4. Given an account-level condition (for example unverified e-mail, paused matching, expiring session), when it applies, then a persistent account banner is shown on member pages until the condition is resolved or the member dismisses it, and a dismissed non-critical banner stays dismissed for 7 days.
5. Given an administrator publishes a site announcement, when members load a page, then the site banner shows in its variant and a dismissed banner stays dismissed on that device.
6. Given the connection is lost or restored, when the browser fires an online/offline event or the API is unreachable, then a connection banner appears with warning/danger and a success banner shows on recovery.
